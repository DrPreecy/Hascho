# Decisions

## DEC-001 — Human-led, AI-supported

Status: Decided
Scope: Project-wide

The human Project Owner makes material decisions. AI explains, researches, challenges, connects, recommends, and helps execute approved work. Assumptions must not be hidden in plans, concepts, or code.

Rationale: The workbench should improve the owner's judgment and capability rather than replace ownership.

## DEC-002 — One workbench instance per project

Status: Decided  
Scope: Product boundary

The future universal workbench is copied, installed, or otherwise attached to each individual project. It adapts locally while maintaining a common base. It is not one giant interface in which all projects are managed.

Rationale: Projects need separation, portable state, focused context, and freedom to evolve independently.

## DEC-003 — Clear transformation sequence, adaptable content

Status: Decided  
Scope: Process architecture

The future workbench should provide an understandable sequence showing transformation from an initial thought to a real outcome. The sequence must be universal and adaptive: project-specific content, optional modules, parallel work, iterations, pauses, and exit paths remain possible.

Rationale: The Project Owner values the orientation and momentum of a stepwise transformation but does not want an insurance-specific or rigid process.

## DEC-004 — Software roadmap is thematic orientation only

Status: Decided  
Scope: Software project modules

The supplied Software Engineering Roadmap is a reference for the subject areas that may matter in software projects. It will not run alongside projects, track the owner's learning, prescribe stages 1–15, or require every topic.

Rationale: Its purpose is to prevent thematic blind spots, not to create a second process.

## DEC-005 — Quality of life includes an active guidance layer

Status: Decided  
Scope: Interaction model

Quality of life includes visible plans, context-aware next actions, differentiated to-dos, suggested prompts or actions, agent scope and progress visibility, checks, and strong pause and resume behavior.

Rationale: The useful coordination behavior of modern coding agents should be available across project work without turning the workbench into an autopilot.

## DEC-006 — Software work needs anti-vibe-coding safeguards

Status: Decided  
Scope: Software project modules

AI-assisted implementation must connect intent, a proportional implementation plan, understandable code, architecture decisions, security, testing, review, and evidence. The system must not equate generated code or a successful build with a trustworthy result.

Rationale: AI speed should not hide poor understanding, unverified behavior, accidental architecture, or security risk.

## DEC-007 — Switchable collaboration modes

Status: Decided
Scope: Interaction model

The future workbench must support explicitly switchable Auto, Co-work, and Co-design modes at an appropriate project, thread, or activity scope. Auto permits only bounded and reversible AI-led work with a traceable report; Co-work supports jointly steered task completion; Co-design supports iterative joint shaping before a recommendation. Switching modes changes collaboration cadence and initiative, not human ownership, approval boundaries, provenance, safety controls, or durable-state requirements.

Rationale: The Project Owner needs both pre-structured AI assistance and genuine participation in forming concepts and choices. A visible, switchable mode prevents either collaboration style from being silently imposed.

## DIR-001 — Adaptive Project Workbench

Status: Provisional direction  
Review gate: R3

The preferred concept is an adaptive workbench rather than a rigid linear wizard.

## DIR-002 — Visual Control Room

Status: Provisional direction  
Review gate: R3/R4

A visual Control Room should make current context, open work, evidence, decisions, risk, and next actions understandable. It will coexist with task-specific views and must not become the canonical data model.
